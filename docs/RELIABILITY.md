# Надёжность: план исправлений 1–4

Область: повтор загрузки, перезагрузка OBS, резервирование слотов, незавершённая нарезка.

1. Перед сетевой загрузкой сохранять состояние `uploading`. При неизвестном результате
   переводить задание в `upload_unknown`, сохранять слот и искать ролик на канале перед повторной загрузкой.
   После перезапуска `uploading` также требует сверки с каналом. Ошибки квот до принятия видео можно повторять.
   Это консервативная защита от дублей; автоматическое восстановление resumable-сессии — отдельная задача.
2. Межпроцессная блокировка очереди на весь срок работы потока. Новый обработчик читает очередь
   только после освобождения блокировки предыдущим. Остановка запрещает новые шаги, текущий завершает запись.
3. Межпроцессная блокировка расписания на всю транзакцию чтения, резервирования/освобождения и записи.
4. Журнал нарезки до запуска FFmpeg; передача готового клипа в очередь с подтверждением и дедупликацией.
   При перезапуске повторять незавершённую нарезку из сохранённого исходника. Состояние запроса OBS,
   для которого ещё не получен путь файла, сохранять отдельно и явно показывать как требующее восстановления.
   Несохранённые кадры в оперативной памяти OBS восстановить после закрытия нельзя.

Проверка: аварийный сетевой ответ, перезапуск в `uploading`, конкурирующие очереди и слоты,
восстановление нарезки и повторная передача одного клипа. YouTube в тестах заменяется заглушкой.

## Реализовано и проверено

- `uploading` сохраняется до запроса; `upload_unknown` удерживает слот, сверяется с каналом и отображается в статусе как `checking`.
  Повтор после ошибки плейлиста использует сохранённый ID. Ошибки квоты допускают повтор.
- `pipeline.lock` удерживается ОС на весь срок работы потока. Новый поток ждёт освобождения,
  затем перечитывает очередь. Входящие задания сохраняются в `inbox/`.
- Расписание перечитывается под блокировкой при резервировании и освобождении.
  Повреждённый JSON очереди/расписания вызывает ошибку вместо сброса состояния.
- `captures/*.json`: `cutting` → `ready` → `done`. Запись предшествует FFmpeg и передаче в очередь.
  При старте незавершённые операции восстанавливаются. Исходный replay удаляется только после стадии `done`.
- `captures/awaiting-*.json` сохраняет запросы без полученного пути replay. При старте последний
  replay OBS сопоставляется по времени с единственным подходящим запросом (окно 30 секунд).
  При отсутствии или неоднозначности файла автоматического угадывания нет.

## Эксплуатация

После правок перезагрузить скрипт OBS. Старый поток заканчивает текущую операцию,
новый ждёт освобождения блокировки. `stop()` не блокирует интерфейс OBS.

`upload_unknown` сверяется с каналом автоматически (см. раздел ниже). Вмешательство нужно только для `failed`:
исправить причину и в остановленной очереди вернуть стадию `upload`. Восстановление resumable-сессий не реализовано:
оборванная загрузка начинается заново после сверки.
Ручная правка очереди допустима только с резервной копией и остановленным обработчиком.

Несохранённые на диск кадры OBS восстановить невозможно; журнал сохраняет сведения о серии.

Проверка: 127 тестов, включая потерю успешного ответа, перезапуск в `uploading`, смену обработчика
во время рендера, поздний replay, сбой передачи готового клипа и конкуренцию резервирований.

## Очередь загрузки: паузы, сверка, повторы (2026-09-13)

Правило: видео не теряется и не загружается дважды. Монтаж Shorts идёт всегда, паузы касаются только загрузки.

| Что случилось | Что делает очередь |
|---|---|
| Квота API на сутки (`quotaExceeded`, `dailyLimitExceeded`) | Пауза всей загрузки до 08:05 UTC (после сброса в полночь по Тихоокеанскому времени). Слот освобождается |
| Лимит загрузок канала (`uploadLimitExceeded`, скользящие 24 ч) | Пауза всей загрузки на час, затем одна пробная загрузка; так каждый час до снятия лимита |
| Частотное ограничение (`rateLimitExceeded`) | Пауза 15 минут |
| Нет входа / отозван токен | Пауза 10 минут, в статусе «YouTube login needed» |
| Сеть оборвалась, ответ не пришёл, OBS упал во время загрузки | `upload_unknown`: слот удерживается, через 10 минут видео ищется на канале по названию и времени публикации. Найдено — считается загруженным. Не найдено 3 раза подряд — слот освобождается и видео загружается заново |
| Ошибка при добавлении в плейлисты | Видео уже на канале (ID сохранён). Повтор с паузой до 1 часа, бесконечно |
| YouTube отверг метаданные (`invalidTitle` и т.п.) | Только это видео → `failed`, файл остаётся на диске, остальные загружаются |
| Пропал файл Short | Short монтируется заново из горизонтального клипа |
| Задания, отложенные старой логикой до следующего дня | При запуске возвращаются в очередь сразу |
| Скрипт перезагружен, пока OBS сохранял буфер для серии | Если OBS не перезапускался и отрезок ещё в буфере, сохранение запрашивается заново; иначе серия пишется в `captures/lost-*.json` с ошибкой в логе (кадры уже не восстановить) |
| Падение между резервированием слота и записью очереди | При старте рабочего потока будущие слоты, которые не принадлежат ни одному видео, освобождаются |
| Канал не удаётся проверить при неизвестном исходе | Повторная проверка с растущей паузой до 1 часа, после 3 неудач ошибка в логе. Повторной загрузки нет, чтобы не создать дубль |
| Выполненное видео ещё не опубликовано | Задание не вычищается из очереди, пока не пройдёт время публикации, чтобы его слот не заняло другое видео |

Пауза хранится в `state.json` (`uploads_paused_until`, `uploads_pause_reason`), переживает перезапуск OBS и видна в статусе панели:
`uploads paused until 13.09 20:42: channel upload limit`.

Проверено 13.09 на копии реальной очереди (8 видео после `uploadLimitExceeded`): 1 проба при старте, 1 проба через час,
после снятия лимита все 8 загружены в уникальные слоты.

Файл буфера OBS удаляется после того, как клип нарезан и передан в очередь (`captures/*.json` в стадии `done`);
завершённые записи журнала удаляются через 7 дней.
